# Правила оформления коммитов

## Введение
Спецификация _Conventional Commits_ - это облегчённое соглашение поверх сообщений коммитов. 
Она предоставляет простой набор правил для создания явной истории коммитов, 
что упрощает использование автоматизированных инструментов для версионирования, создания релизов и т.п.
_Conventional Commits_ хорошо согласуется с _SemVer_, описывая функции, 
исправления и критические изменения в сообщениях коммитов.

Сообщение коммита должно быть структурировано следующим образом:
```text
<тип>[необязательная область действия]: <описание>
[необязательное тело]
[необязательные сноски]
```

Коммит содержит следующие типы коммитов для передачи намерений:
- `feat:` добавляет новую функцию в кодовую базу (соответствует `MINOR` в семантическом версионировании)
- `refactor:` правки кода без исправления ошибок или добавления новых функций
- `fix:` исправляет ошибку в кодовой базе (соответствует `PATCH` в семантическом версионировании)
- `BREAKING CHANGE:` вносит критическое изменение API (соответствует `MAJOR` в семантическом версионировании)
- `docs:` обновление документации
- `style:` правки по стилю оформления (табуляция, отступы, кодировки и т.д.)
- `revert:` откат на предыдущие коммиты
- `test:` добавление и изменение тестов
- `ci:` настройка CI/CD, скрипты и автоматизация
- `build:` сборка проекта или изменения внешних зависимостей
- `perf:` изменения, направленные на улучшение производительности

К типу коммита может быть добавлена область для предоставления дополнительной контекстной информации,
она заключается в круглые скобки, например: 
```text
feat(parser): add ability to parse arrays.
```

Типы коммитов кроме `feat`, `fix` и `BREAKING CHANGE` не имеют неявного эффекта в семантическом версионировании.

Могут быть предоставлены сноски, отличные от `BREAKING CHANGE: <описание>`, которые следуют соглашению, 
аналогичному формату `git trailer`. В частности, сноски часто используются для ссылок на связанные задачи (issues) - 
например, `Refs: #123` или `Closes: #42`.

## Примеры

#### Сообщение коммита с описанием

```text
feat: allow provided config object to extend other configs
```

#### Сообщение коммита с описанием и сноской о критическом изменении
```text
feat: allow provided config object to extend other configs
BREAKING CHANGE: `extends` key in config file is now used for extending other config files
```
#### Сообщение коммита без тела
```text
docs: correct spelling of CHANGELOG
```

#### Сообщение коммита с областью
```text
feat(lang): add Russian language
```

#### Сообщение коммита со ссылкой на задачу (issue)
```text
fix: prevent racing of requests

Introduce a request id and a reference to latest request.
Dismiss incoming responses other than from latest request.
Remove timeouts which were used to mitigate the racing issue but are obsolete now.

Closes: #321
```

#### Сообщение коммита с многострочным телом и несколькими сносками
```text
fix: prevent racing of requests
Introduce a request id and a reference to latest request.
Dismiss incoming responses other than from latest request.
Remove timeouts which were used to mitigate the racing issue but are obsolete now.
Reviewed-by: Z
Refs: #123
```

## Связь с задачами (issues)
Хотя спецификация напрямую не предписывает конкретных токенов для задач, 
общепринятой практикой в системах вроде GitHub, GitLab и Jira 
является помещать ссылки на связанные issues в секцию сносок. 
Для этого достаточно использовать знакомые по `git trailer` токены: `Refs`, `Closes`, `Fixes` или `Resolves`, 
и указывать после них номер задачи (например, #42 или полную ссылку).

- `Refs: #<номер>` - связывает коммит с задачей, не закрывая её. 
Используйте, когда коммит относится к задаче, но не решает её полностью.
- `Closes: #<номер>` (или `Fixes:`, `Resolves:`) - автоматически закрывает задачу при мерже коммита в ветку по умолчанию 
(в GitHub распознаются слова `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`). 
Согласно формату _Conventional Commits_, такое ключевое слово выступает в роли токена сноски.

## FAQ
#### Зачем использовать Conventional Commits?
- Автоматическое создание _CHANGELOG_.
- Автоматическое определение изменения семантической версии (на основе типов внесённых коммитов).
- Информирование о характере изменений коллег, общественности и других заинтересованных сторон.
- Запуск процессов сборки и публикации.
- Упрощение участия в ваших проектах за счёт предоставления более структурированной истории коммитов.

#### Как это соотносится с SemVer?
- Коммиты типа `fix` должны приводить к выпускам `PATCH`. 
- Коммиты типа `feat` должны приводить к выпускам `MINOR`. 
- Коммиты с `BREAKING CHANGE`, независимо от типа, должны приводить к выпускам `MAJOR`.

#### Что делать, если коммит соответствует более чем одному типу?
По возможности вернитесь назад и сделайте несколько коммитов. 
Часть преимущества _Conventional Commits_ заключается в их способности 
побуждать нас делать более организованные коммиты и PR.

#### Что делать, если я использовал неправильный тип коммита?
###### Когда вы использовали тип, предусмотренный спецификацией, но неверный, например, fix вместо feat:
Перед слиянием или выпуском ошибки мы рекомендуем использовать `git rebase -i` для редактирования истории коммитов. 
После выпуска способ исправления будет зависеть от используемых вами инструментов и процессов.

###### Когда вы использовали тип, не предусмотренный спецификацией, например, feet вместо feat:
В худшем случае, это не конец света, если коммит попадёт в историю, не соответствующий спецификации Conventional Commits. 
Это просто означает, что данный коммит будет пропущен инструментами, основанными на спецификации.

#### Как Conventional Commits обрабатывает коммиты отката (revert)?
_Conventional Commits_ не предпринимает явных усилий для определения поведения отката. 
Одна из рекомендаций - использовать тип `revert` и сноску, 
которая ссылается на SHA коммитов, которые откатываются, например:
```text
revert: let us never again speak of the noodle incident
Refs: 676104e, a215868
```
